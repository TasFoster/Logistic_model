## Уровень 0. Идея и архитектура <a name="уровень-0"></a>

**Одна конфигурация центра — один граф. Два независимых движка читают его и считают
по-разному.**

```
              ┌───────────────────────┐
              │   Файл графа (JSON)    │  узлы, рёбра, ресурсы, буферы, направления
              └───────────┬───────────┘
                          │ (один контракт)
            ┌─────────────┴──────────────┐
            ▼                            ▼
  ┌───────────────────┐        ┌───────────────────┐
  │ АНАЛИТИКА          │        │ ИМИТАЦИЯ (DES)     │
  │ core/analitic      │        │ core/simulator     │
  │ стационарные       │        │ события во времени │
  │ балансы «в час»    │        │ очереди, блокировки│
  └─────────┬──────────┘        └─────────┬──────────┘
            │ analytic_metrics.csv         │ metrics.csv
            └──────────────┬───────────────┘
                           ▼
                 ┌───────────────────┐
                 │ СВЕРКА             │  узел — аналитика — симуляция — Δ%
                 │ core/validation    │
                 └───────────────────┘
```

**Почему именно две модели, а не одна.** Они отвечают на разные вопросы:

| | Аналитическая модель | Имитационная модель |
|---|---|---|
| Ось времени | нет, только интенсивности «штук в час» | проживает события минута за минутой |
| Отвечает на | «сколько нужно ресурсов и что в среднем?» | «как система ведёт себя во времени?» |
| Видит | средние потоки, загрузки, штат, парк, площадь | очереди, блокировки, каскады, пики, время в центре |
| Роль | **проектирует** конфигурацию | **стресс-тестирует** её |

Правило разделения: аналитика отвечает на всё, что формулируется через «в час» и
«в среднем», и молчит про «ждёт», «накопилось», «в момент времени» — это зона
симуляции. Второй смысл двух моделей — **взаимная проверка**: два независимых способа
посчитать одно и то же обязаны сойтись (этим занимается `core/validation`).

**Ключевой инвариант независимости:** модели не импортируют друг друга и не
«подглядывают» в чужие ответы. Единственный модуль, которому разрешено импортировать
обе, — сверка. Иначе сверка проверяла бы согласие модели с самой собой.

## Уровень 1. Общий контракт — файл графа <a name="уровень-1"></a>

Граф — декларативный JSON. Обе модели трактуют его поля **одинаково** (иначе сверка
бессмысленна). Поддерживаются две формы записи — актуальная «контрактная» (узлы/рёбра
списком, поля `*_list`) и ранняя «прототипная» (словарём) — читаются наравне.

### Узел

```json
{
  "id": 2, "name": "unKTU", "type_node": "transform",
  "input":  {"KTY": 1},
  "output": {"Product": 27, "Box": 1},
  "effecive_ellements": [{"name": "mashin", "ef": 4000}],
  "pos": {"x": 2, "y": 2}, "scale": {"width": 100, "height": 100}
}
```

Семантика полей (это и есть «контракт совместимости»):

| Поле | Смысл |
|---|---|
| `effecive_ellements[].ef` | производительность единицы ресурса, **шт/ч = срабатываний/ч**. Мощность узла = **Σ ef**. Время обработки (нужно только симуляции) = 3600/ef |
| `output {тип: N≥1}` | **детерминированное размножение**: 1 срабатывание → N сущностей (1 КТЯ → 27 товаров + 1 короб) |
| `output {тип: доля<1}` | **вероятностная развилка**: 1 сущность, выбранная по долям (сортировка 0.95 товар / 0.05 nonsort) |
| `input {тип: N}` | **сборка**: сколько сущностей каждого типа нужно на 1 срабатывание (упаковка: 27 товаров + 1 короб) |
| `type_node` | роль: `Input`/`transform`/`sort`/`split`/`pack`/`Storage`/`source` |

**Единицы `ef` — критично.** `ef` считается в *срабатываниях узла в час*, а не в
«товарах». Проверено на эталоне: `unKTU ef=4000` = 4000 **КТЯ/ч** (на входе КТЯ);
`Pack ef=1500` = 1500 **КТЯ_full/ч** (хотя на входе 27 товаров); `Sort1 ef=10000` =
10000 **товаров/ч**. Половина ошибок таких моделей — спутать единицы; поэтому поток —
всегда пара «число + тип сущности».

### Ребро

```json
{"node_in_id": 2, "node_out_id": 3, "storage": 2000, "type_el": "Product",
 "dest_group": 0, "pool": "forklift", "batch": 100}
```

| Поле | Смысл |
|---|---|
| `type_el` | какой тип сущности течёт по ребру |
| `storage` | ёмкость буфера ребра; при переполнении узел-источник блокируется |
| `dest_group` | группа направлений (для 2-й стадии сортировки) |
| `pool`, `batch` | мобильный ресурс (погрузчик), обслуживающий ребро, и размер партии на рейс |

### Граф целиком

`input_stream` (товаров/ч), `type_input` (палета), `start_node_id`, `type_output`
(что отгружаем), `directions` (400 направлений, профиль Парето 20/80, число групп),
`resource_pools` (погрузчики), `transport` (расстояния/скорость для времён рёбер).

Особые узлы:
- `Storage` — сток (nonsort, брак тары): потребляет, ничего не порождает, мгновенный.
- `source` — машина новых КТЯ: восполняет **дефицит** тары в целевом ребре
  (`target_rib`, `low`); её выработка эмерджентна.

## Уровень 2. Аналитическая модель (`core/analitic`) <a name="уровень-2"></a>

Считает стационар: интенсивности потоков, загрузки, размерение ресурсов, штат, парк,
площадь. Без оси времени и без зависимости от SimPy (чистый Python).

Модули: `loader` · `balance` · `directions` · `resources` · `facility` + `norms` ·
`metrics` · `run`.

### 2.1. `loader.py` — чтение и нормализация

Читает JSON (обе схемы), приводит к каноническому виду:
`{id, name, type, inputs, outputs, rates[], n_units, capacity=Σef, params, pos, scale}`.
Мирроринг логики загрузчика симулятора — ради идентичной трактовки полей (в шапке
файла TODO объединить загрузчики в общий модуль).

**Интенсивность входа.** `arrival = input_stream / товаров-на-палету`. Число
товаров-на-палету считается проходом по цепочке от стартового узла, перемножая
детерминированные коэффициенты до появления товара (палета → 20 КТЯ → 27 товаров =
540). Та же формула, что в симуляторе, — обе модели берут одинаковый вход
(185.2 палет/ч под 100 000 товаров/ч).

### 2.2. `balance.py` — решатель балансов (главный алгоритм)

Считает активность каждого узла **λ** (срабатываний/ч), потоки по рёбрам, загрузки,
узкое место, предельный поток.

**Модель потока.** Активность узла λ связывает вход и выход:
- выход типа `t` из узла = `λ · output[t]` (и для размножения N≥1, и для доли <1);
- потребность типа `t` = `λ · input[t]`;
- λ узла определяется «главным» входом: `λ = приток(главный) / input[главный]`.
  Для сборки упаковки главный вход — товары (27), а тара закрывается источником.

**Алгоритм (пошагово):**

1. **Топологический порядок** не-source узлов по рёбрам (алгоритм Кана). Рёбра
   образуют DAG (цикл оборота тары замкнут не ребром, а узлом-источником), поэтому
   один проход считает почти всё.
2. **Проход по узлам** в топопорядке:
   - стартовый узел: `λ = arrival`;
   - прочие: `λ = min по главным входам (приток / input[t])`;
   - раскладка выходов по исходящим рёбрам. Если рёбер одного типа несколько
     (2-я стадия: 1 сортировщик → 20 секций), поток делится **по доле объёма группы
     направлений** (см. 2.3), иначе поровну.
3. **Источники** (`source`): считаются после основного прохода. Активность источника =
   `max(0, спрос приёмника − прочие поступления)`. Для эталона: спрос упаковки в
   коробах 3 518/ч, реюз от развилки тары 2 963/ч → машина новых КТЯ добирает 555/ч.
4. Для общности проход повторяется несколько раз (на DAG сходится за 1 итерацию).

**Результаты на узел:** `throughput = λ`, `capacity = Σef`, `load = λ/capacity`.
- **Узкое место** = узел с максимальной загрузкой.
- **Предельный поток** = `input_stream / загрузка_узкого_места` (все потоки линейны
  по входу, поэтому масштабирование точное): на эталоне 100 000 / 0.926 ≈ 108 000 тов/ч.

### 2.3. `directions.py` — профиль 400 направлений (порт)

Из постановки: направления неравнозначны — «верхние 20% забирают до 80% объёма».
Реализация — степенной закон (Zipf) `w(i) = 1/(i+1)^alpha`.

- **Подбор alpha** бисекцией: ищем показатель, при котором верхние 20% направлений
  дают ровно 80% объёма (для 400 направлений `alpha ≈ 1.08`).
- **Балансировка «змейкой»**: направления сортируются по убыванию объёма и
  раскладываются по 20 группам змейкой, чтобы объёмы групп были максимально равны.
  Но самое жирное направление (~18 600 тов/ч) неделимо → доли групп всё равно
  неравны (от 2.9% до 20.4%). Именно под это сделаны разные мощности секций
  2-й стадии (4 000…25 000 шт/ч).
- `group_volume_shares()` — доли объёма по группам; их использует решатель балансов
  для деления потока (2.2, шаг 2). Порт математики из симулятора — чтобы доли
  совпадали до машинного нуля (проверено сверкой, см. Уровень 4).

### 2.4. `resources.py` — размерение ресурсов

Вопрос «сколько единиц купить»: `needed = ceil(throughput / производительность_единицы)`
(округление вверх — вниз оставило бы узел перегруженным). Сравнение «есть/надо»
показывает запас (Sorting 11/10, Pack 4/3) или дефицит.

### 2.5. `facility.py` + `norms.py` — штат, парк, площадь

Надстройка над балансами. Все нормативы — в `norms.py`, с пометками источника:
**[PDF]** (из условия) и **[ДОП]** (проектное допущение, обосновывается в отчёте).

- **Штат:** классификатор ролей узлов + правила. Автосортировщик — загрузчики
  `throughput/1000` [PDF: 1 чел на 1000 тов/ч] → 100 человек; ручная сортировка
  `throughput/250` [PDF] → 20 человек; прочее — операторы обслуживания на единицу [ДОП].
- **Парк:** число нужных единиц по машинным ролям + погрузчики из `resource_pools`.
- **Площадь:** `( Σ площадь_оборудования(единицы) + Σ площадь_буферов(ёмкость ребра ×
  габарит тары) + накопители упаковки ) × коэф. проходов 1.35`. Габариты палеты
  (0.96 м²) и КТЯ (0.24 м²) — [PDF]; площади установок и проходы — [ДОП].

Итог на полном графе: **штат 163 чел** (против 800 при ручной схеме), **площадь
15 809 м²** (< ориентира 20 000–24 000).

### 2.6. `metrics.py` — выгрузка в общий формат

CSV `object, metric, value, unit` — тот же контракт, что у симулятора, поэтому
сверка = построчное сравнение. По узлам `throughput`+`utilization` пересекаются с
метриками симуляции; остальное (мощность, размерение, потоки рёбер, штат, площадь,
предел) — аналитическое.

### 2.7. `run.py` — CLI

`python -m core.analitic.run --graph … [--input-stream N] [--out DIR]` — печатает
сводку (загрузки, размерение, штат/парк/площадь, направления) и пишет CSV.

## Уровень 3. Имитационная модель (`core/simulator`) <a name="уровень-3"></a>

Дискретно-событийная симуляция (DES) на **SimPy**: проживает граф во времени с
очередями, ограниченными буферами и блокировками.

### 3.1. `graph_loader.py` — нормализация

Тот же контракт, что читает аналитика (Уровень 1). Дополнительно считает времена
рёбер (по координатам `pos` и `transport`) и время обработки `service = 3600/ef`.

### 3.2. `model.py` — ядро DES

Три сущности:
- **`Entity`** — единица потока: тип + момент рождения + направление (для товаров).
- **`Rib`** — ребро = `simpy.Store(capacity=storage)`. Этот же буфер служит входной
  очередью узла-приёмника. **Полный буфер → `put` приостанавливает воркера-источника
  → блокировка** (и каскадная деградация вверх по цепочке). Это ключевой механизм:
  очереди и заторы возникают «бесплатно» из ограниченной ёмкости.
- **`Node`** — набор параллельных воркеров-процессов SimPy. Цикл воркера:
  1. собрать вход по `inputs {тип: кол-во}` (**голодание**, если входа не хватает);
  2. держать `service` секунд (**работа**);
  3. выдать выход по `outputs` в рёбра (**блокировка**, если буфер полон).

**Правила выходов** те же, что в контракте: N≥1 — размножение; доля<1 — вероятностная
развилка (бросок ГПСЧ по долям); сборка — воркер копит нужное число входов.

**Учёт времени.** Всё время воркеров раскладывается на 4 доли:
**работа + блокировка + голодание + отказ = 100%** (защищено тестом). Это позволяет
отличить *блокировку* (выходной буфер полон) от *голодания* (не хватает входа) — разные
болезни с разным лечением.

**Специальные механизмы:**
- **Источник палет** — внешний генератор с интервалом `3600/arrival`.
- **Машина новых КТЯ** (`source`) — держит уровень тары в целевом ребре не ниже `low`.
- **Погрузчики** (`resource_pools`) — не узлы, а пул на рёбрах: ребро копит партию
  `batch`, берёт свободную единицу, та едет туда-обратно. Нехватка погрузчиков душит
  линию каскадом (защищено тестом).
- **Упаковка по направлениям** (`by_direction`): товар несёт направление от вскрытия;
  упаковка копит 27 товаров ОДНОГО направления в ячейке-накопителе; если направление
  вялое и КТЯ не набрался за `flush_timeout`, он уезжает недозаполненным.
- **Отказы** (`outages`) — узел выводится из строя на интервал (сценарии).

### 3.3. `directions.py` — профиль + выборка

Тот же Zipf + балансировка, что портирована в аналитику, плюс `sample()` — выборка
направления для конкретного товара (бисекция по накопленным вероятностям).

### 3.4. `metrics.py` — метрики

CSV `object, metric, value, unit`; агрегация по интервалам **1 мин / 1 ч / 12 ч /
24 ч** (требование критериев). Узкое место = узел с макс. (работа + блокировка).
Метрики считаются на установившемся участке (после прогрева).

### 3.5. Остальное

- `run.py` — CLI-запуск + текстовая сводка (загрузки, тара, направления, погрузчики,
  отгрузка).
- `scenarios.py` — сценарии: пик ×1.5/×2, рост nonsort, отказы узлов; сравнительная
  таблица.
- `viz.py` — 2D-план цеха в самодостаточном HTML (блоки-аппараты с загрузкой,
  конвейеры-стрелки, тепловая карта). Без интернета — для изолированного сервера.
- `test_smoke.py` — 24 теста физической согласованности (баланс тары, 27→1, 100k/ч,
  палета=20 КТЯ, 24 ворот, 250 тов/ч на человека, каскады и т.д.).

## Уровень 4. Сверка моделей (`core/validation`) <a name="уровень-4"></a>

`compare.py` — потребитель обеих моделей (единственный, кому это можно). Алгоритм:

1. Запустить аналитику: `λ`, загрузки по узлам.
2. Запустить симуляцию N часов: throughput = обработано/окно, загрузка = работа/время.
3. Сопоставить узлы по имени → таблица `узел — аналитика — симуляция — Δ% — Δпп`.
4. Отдельно сверить **профиль направлений**: доли групп из аналитики (порт) и из
   симулятора (оригинал) обязаны совпасть до машинного нуля.
5. Вердикт: сколько узлов сходятся в пределах 5%, кто выпадает > 10% и почему.

**Интерпретация расхождений** (это находка, не баг): крупные Δ только у эмерджентной
тары (машина новых КТЯ, брак — зависят от динамики буфера) и на выходной стороне
(симуляция ловит backpressure — до ворот доходит ~90–95% номинала, аналитика считает
идеал). Основная цепочка и все 20 секций 2-й стадии сходятся в пределах ~1–2%; профиль
направлений — идентичен (Δ = 0).

## Уровень 5. Ключевые числа и находки <a name="уровень-5"></a>

| Величина | Значение |
|---|---|
| Вход | 100 000 товаров/ч = 185 палет/ч = 3 704 КТЯ/ч |
| Узкое место (аналитика) | вскрытие КТЯ `unKTU`, загрузка ~92.6% |
| Предельный поток | ~108 000 товаров/ч (эталон) |
| Выход | ~10 машин/ч; время товара в центре ~50 мин |
| Штат | **163 чел** (против 800 при ручной схеме) |
| Площадь | **15 809 м²** (< ориентира 20 000–24 000) |
| Сверка | секции 2-й стадии ≤ 2%, профиль направлений идентичен |

**Содержательные находки:**
1. **Затор по таре.** Без развилки тары излишки пустых коробов копятся, буфер
   забивается, вскрытие блокируется на ~45% — теряется ~60% пропускной способности.
   Решение: развилка 80/20 + сток брака + машина новых КТЯ.
2. **Группировка направлений критична.** Наивная нарезка «подряд» из-за Парето
   перегружает первые секции и душит 1-ю стадию (−56% выхода). Нужна балансировка.
3. **Пик не увеличивает выход, а копит очередь.** При +50/+100% входа выход упирается
   в потолок, время в центре растёт с 10 до 35–50 мин.
4. **Backpressure.** Сквозной выход ~90–95% номинала: у предела буферы насыщаются.
